## What shipped

Origin story: discussing README updates for the newly-published `bookie-mcp` npm package surfaced that nothing verifies the published artifact actually installs and runs. This adds a second CI job, `verify-npm-install`, to `npm-publish.yml`: after `npm publish` succeeds, it installs the just-published version from the registry into a throwaway directory, creates a disposable Neon project, pushes the bundled Prisma schema, starts the server, and confirms it responds over stdio (MCP inspector `tools/list`, asserting `add_transaction` is present) — then always deletes the Neon project. This is the exact "no clone" flow newly documented in `README.md`.

The full flow (project creation → schema push → server start → tools/list → project deletion) was manually dry-run once against a real disposable Neon project before this report was written — confirmed working end-to-end, not just typechecked.

**Post-review addition (human follow-up question, not a review finding):** "does the pipeline clean up after each test, and if it fails does it log an issue?" — cleanup was already correct (`try/finally`, confirmed above), but failure visibility wasn't: a failed run was only a red check in the Actions tab. Added a `File a GitHub issue on failure` step (`if: failure()`, job-scoped `issues: write`) that opens an issue titled `verify-npm-install failed for <tag>`, or comments on an existing open one with the same title if the same version fails again (dedup via `gh issue list --search`, not a label — avoids needing a pre-existing label in the repo). YAML validated with `python3 -c "import yaml; yaml.safe_load(...)"` since GitHub Actions syntax can't be typechecked by `tsc`.
